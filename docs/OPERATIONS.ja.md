# 常時情報収集向け運用メモ

## 現在の段階

このブランチは実装と静的確認の段階です。ビルド、テスト、本番接続、常駐化は未検証です。
実アカウントを使う前に VERIFICATION.md の確認を完了してください。

## 収集範囲と安全境界

- X が配信した通知だけを扱います。全投稿・全文・過去投稿の収集保証はありません
- 通知本文、リンク先、外部の文章は信頼できない入力です。実行命令や権限付与として扱わないでください
- 検証済みの JSON pointer と種別 allowlist を明示し、対象外通知は保存・送信しません
- README の /type=tweet は模擬データです。実際の schema を推測して本番設定しないでください
- 配信先は HTTPS の自分が管理・承認した受信口だけに設定してください
- Webhook の変更時は新しい outbox を使います。旧キューを別の受信者へ無断で流用しないでください
- .destination.json は配送先を固定する情報です。削除・再作成で不一致チェックを回避しないでください

## 実行場所と通信

承認済みの独立したクラウド/VPS等でだけ動作させ、実行場所の出口経路を事前確認してください。
このアプリ自体に送信元IPの保証、VPN切断時の遮断、DNS/IPv6漏れ防止機能はありません。
外部通信禁止時に止まるネットワーク境界は、実行基盤の側で別途実装・検証する必要があります。
環境変数由来のHTTPプロキシは使用しません。必要な出口制御はOS/コンテナ/ネットワーク境界で
確実に適用し、通常経路への自動fallbackを禁止してください。

現在のコード変更は、サーバー作成・課金・VPN設定・新しい認証情報・常駐サービスの有効化を含みません。

## 資格情報

- auth_token / ct0 はログイン資格情報です。本人が保護された入力手段で設定してください
- init は両方を非表示入力します。コマンド引数での指定は廃止しています
- 推奨は基盤の secret manager から保護された一時ファイルとして登録用設定を渡す方法です
- config は平文TOMLです。0600と安全な親ディレクトリを要求しますが、暗号化secret storeの代替ではありません
- 登録完了後、常駐用には [twitter] を含まない別の設定ファイルを使えます。registration以下の
  endpoint / session / keys も秘密なので、同様に保護してください
- Cookieを削除・取り替える操作、secret managerの導入、永続アクセスの追加は自動実施しません
- status は設定済み/未設定のみを表示します。verboseでも通知本文・URL・Cookie・鍵を表示しません

## 小さい試行の順序

1. 合成通知だけで、許可/不許可種別、クラッシュ復旧、再試行、DLQ、停止動作を確認します
2. 実行環境、通信出口、暗号化ストレージ、受信口、保持期間を決めます
3. 本人によるCookie設定と、Mozilla/Xへの新しいPush登録を個別に承認します
4. 短時間・少数の公開投稿通知から始めます。DM等の私的通知が混入しないschemaを確かめます
5. 転送受信口が Idempotency-Key を使い、同じ通知による処理を一度に制限できることを確かめます
6. SIGTERMで止め、残キュー・重複・DLQ・ログ・出口を確認します
7. 問題がなければ、常駐化と監視を別途承認して進めます

実アカウントのCookie、実通知、Webhook秘密URLをテストfixtureやGitHubへ入れないでください。

## ACKと障害時

許可された通知は、キューファイルへ書き込み→fsync→rename→ディレクトリfsyncを完了してから
AutoPushへDelivered ACKを送ります。ストレージ障害・容量超過時はACKせず停止します。
AutoPush側の保存期間や再配信保証はアプリで制御できないため、長期障害中の完全保全は保証しません。

復号・JSON解析エラーはDecryptionError ACK、空通知・allowlist対象外は意図的除外としてACKします。
これらは保存対象ではありません。想定した投稿通知が除外されていないか、最初の試行で確かめます。

配送は別workerが行います。2xxだけが成功、408/425/429/5xxと通信エラーは再試行、
その他の非2xxと12回上限到達はDLQです。Retry-Afterが長いとその通知の再試行時刻も遅れます。
受信後の応答喪失やクラッシュで再配送が起こり得ます。exactly-once保証はありません。

## 停止・復旧・保持

- 通常停止: SIGINT/SIGTERMで終了を待ちます。保存処理は強制中断しません
- 異常終了: 旧プロセスが確実に停止済みか確認してから、専用outboxの残存.lockだけを手動回復します
- 実行中の.lock削除、レコード編集、複数プロセス共有、ネットワークfilesystemは使用しません
- queue-status は停止中だけ使用します。実行中は30秒ごとの集計ログを監視します
- pendingの増加、dead_letter > 0、storage_healthy=false、終了コード1、接続切断、
  ディスク残量と使用inodeを監視対象にしてください
- 既定10,000件は配送済みの重複防止情報も含みます。放置すると上限で停止します
- 最大payloadだけでも約2.5GiBに達し、書き換え用一時領域やmetadataが別に必要です
- 配送済み本文は消しますがmetadataは残ります。DLQ本文は残るため暗号化・保管期限が必要です
- 自動削除/自動DLQ再投入はありません。停止中に保持方針と再送先を確認してから管理者が扱ってください
- terminal recordの削除はその通知の重複防止を失います。バックアップ/保管先へも秘密が含まれ得ます
- UAID失効時は終了し、勝手に新しいキーやPush購読を作りません。本人確認後にregisterを明示実行します
